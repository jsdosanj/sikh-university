# Contributing

Sikhi University is one Cloudflare Worker: `worker.js` dispatches `/api/*` to `functions/api/*`
(D1 + R2 + Workers AI + KV bindings), and serves the built Astro site (`web/dist`) for
everything else. **Run it with `wrangler dev`, not just the Astro dev server** — `cd web &&
npm run dev` only serves the frontend, so every `/api/*` call 404s and you can't actually
verify auth, enrollment, quizzes, etc. locally.

## Quickstart

```bash
git clone <repo> && cd sikh-university
npm install          # installs wrangler (root devDependency only)
npm run db:seed      # applies schema.sql to a local D1 database (safe, local-only)
npm run dev          # wrangler dev — builds web/ and serves the Worker + API together
```

Open the URL `wrangler dev` prints (defaults to `http://localhost:8787`). The first run is
slower: the `[build]` step in `wrangler.toml` runs `cd web && npm install && npm run build`
before the Worker starts.

This gives you a real local backend: local D1 (seeded by `db:seed`), local R2, local KV, and
Workers AI — none of it touches production. `npm run deploy` (`wrangler deploy`) and
`npm run db:seed:remote` are the production-touching equivalents; don't run those for normal
dev/testing.

### Auth in local dev
Sign-in emails go through Resend, gated by `RESEND_API_KEY`. Locally that secret is unset, so
`POST /api/auth/request` returns the magic-link URL directly in the JSON response
(`devLink`) instead of emailing it — copy that URL into your browser to sign in. See
`.dev.vars.example` (copy to `.dev.vars`, gitignored) if you want to override this.

### Frontend-only iteration
`npm run dev:frontend` (`cd web && npm run dev`) runs just the Astro dev server — faster
reload for pure UI/CSS work, but **no `/api/*` routes exist in that mode**. Don't use it to
verify anything that touches auth, enrollment, progress, or any other API-backed feature.

## Making and verifying a change

1. Branch off `master`: `git checkout -b feat/short-description`.
2. Make the change.
3. Run it for real against `npm run dev`, not just a syntax check:
   - `curl localhost:8787/api/me` → `{"user":null}` confirms the Worker + API are up.
   - Exercise the actual route(s) your change touches (e.g. request a magic link, follow the
     `devLink`, then re-check `/api/me` returns the signed-in user).
4. If you touched the course catalogue, run `python3 scripts/validate.py` (same check CI runs).
5. If you touched frontend/Worker JS, a quick sanity check CI also runs:
   `node --check worker.js` / `node --check path/to/your/file.js`.

## Branch → PR → CI → merge

- Push the branch and open a PR against `master`.
- CI (`.github/workflows/ci.yml`, job `validate`) runs `node --check` on the frontend/Worker/
  Functions JS and `python3 scripts/validate.py` on the course catalogue. `master` requires
  the `validate` check to pass before merging.
- Enable auto-merge on the PR (`gh pr merge --auto --squash`); once `validate` is green it
  merges on its own — no manual review gate.
- Production deploy follows from `master` (see `docs/DEPLOY.md`); you don't deploy manually
  for normal changes.

## Adding/editing a course (brief)

The source of truth is `site/assets/data/courses.json`. Edit the course/lesson/quiz entries
there, then run `python3 scripts/validate.py` to catch missing fields, bad topic IDs,
duplicate course IDs, or malformed quiz answers before opening a PR. Some derived data is
regenerated by scripts in `scripts/` (e.g. `build_paths.py`, `build_quiz_keys.py`,
`build_reader_chapters.py`, `build_source_snippets.py`) — run the one relevant to what you
changed. A fuller course-authoring guide can follow later; this is enough to get a course
change through CI.
